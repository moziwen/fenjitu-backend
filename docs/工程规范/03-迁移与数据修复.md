# 03｜迁移与数据修复

## 模型变更

- 数据库结构只能经版本化迁移进入共享环境；禁止把本地模型同步命令或临时手工改表当成生产发布流程。
- 迁移前评估现有数据量、锁表时间、旧代码兼容性、默认值和回填成本。优先采用可分阶段上线的“扩展—迁移数据—切换读取—收缩”方式。
- 索引应对应真实查询条件与排序；检查写入代价、索引体积和是否与现有索引重复，不因单次慢查询盲目增加。
- 数据库连接凭据按环境管理。本地连不上生产数据库不代表迁移已执行，也不意味着需要复制生产密钥到本地。

## 历史数据修复

1. 先用只读查询确定异常定义、影响范围和样本，区分源数据缺失、映射错误、媒体服务不可用与客户端展示问题。
2. 修复脚本默认预览：报告候选数量、跳过原因和变更前后摘要；真正写入必须有明确授权、精确条件和可重复执行的设计。
3. 生产执行前备份并验证备份可读；按批次处理，记录处理数量，避免全表无条件更新或删除。
4. 修复后再次只读核对，并验证相关接口。不能只凭脚本退出码宣布数据正确。

## 回滚边界

代码回滚不等于数据库回滚。每个不可逆变更都要提前说明恢复办法、备份位置和可能的数据损失窗口；未确认恢复路径时暂停执行高风险迁移。
